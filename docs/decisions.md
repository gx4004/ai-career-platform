# Career Workbench — Decision Log

**Status:** append-only canonical record
**Last reviewed:** 2026-07-10 (D-068–D-075 added same day, R12)

Use this log for durable product or architecture choices. New entries get the next
ID. To reverse a decision, add a new entry and mark the old one `superseded`; do not
erase history.

| ID | Status | Decision | Rationale |
|---|---|---|---|
| D-001 | accepted | Build one connected workspace around six tools, not six standalone generators. | Context reuse and workflow continuity are the product advantage. |
| D-002 | accepted | Use React 19 with TanStack Start/Router for the frontend and FastAPI for the API. | Matches the existing implementation and team familiarity. |
| D-003 | accepted | Keep tool metadata centralized in `frontend/src/lib/tools/registry.ts`. | Prevents ordering, routing, and capability drift. |
| D-004 | accepted | Use a shared execution pipeline for all six tool endpoints. | Centralizes sanitization, caching, persistence, response shape, and observability. |
| D-005 | accepted | Blend deterministic and model scoring only for Resume Analyzer and Job Match. | Generative tools do not have an honest universal score. |
| D-006 | accepted | Use Vertex AI Gemini as the V1 generation provider. | Reduces abstraction and operational scope before product validation. |
| D-007 | accepted | Resume and Job Match may fall back to deterministic analysis; generative tools fail explicitly. | A fake generated artifact is worse than a clear failure. |
| D-008 | accepted | Keep access and refresh tokens in HttpOnly cookies. | Reduces token exposure to browser script. |
| D-009 | accepted | Allow guest tool runs but persist only authenticated runs. | Delivers value before signup without creating anonymous server data. |
| D-010 | accepted | Make `ToolRun` revisions append-only via `parent_run_id`. | Preserves history, comparison, and auditability. |
| D-011 | accepted | Keep workflow context tab-scoped in `sessionStorage`. | Simple continuity without cross-tab synchronization complexity. |
| D-012 | accepted | Use BeautifulSoup first and Playwright as a bounded fallback for job import. | Provides a fast common path and graceful support for rendered sites. |
| D-013 | accepted | Use an in-process result cache for the initial single-instance posture. | Avoids infrastructure before scale requires distributed caching. |
| D-014 | accepted | Ship English-only for V1. | Keeps product and QA scope realistic. |
| D-015 | accepted | Use a responsive web product; do not build native mobile apps in V1. | One surface covers the validation stage. |
| D-016 | accepted | Keep the admin experience inside the main frontend under `/admin/*`. | Avoids a second frontend and duplicated auth/session logic. |
| D-017 | accepted | Use Railway as the intended initial hosting platform. | Existing deployment configuration and integrated PostgreSQL reduce ops work. |
| D-018 | accepted | Keep Sentry payloads scrubbed and disable default PII collection. | Resume and application content are sensitive. |
| D-019 | accepted | Keep monetization gates disabled during thesis/demo mode. | Unrestricted evaluation is more important than revenue validation in this mode. |
| D-020 | superseded by D-046 | Treat public monetization as a post-activation experiment, not a launch blocker. | R9 now defines the evidence gate and provisional experiment posture precisely. |
| D-021 | accepted | Perfect and freshly verify the existing product before major feature expansion. | New scope should build on reliable, accessible, privacy-safe, and visually verified workflows. |
| D-022 | accepted | Make a premium, browser-editable, ATS-aware CV Studio the flagship expansion. | CV creation, scoring, job-specific tailoring, versioning, and DOCX/PDF export deepen the existing Resume and Job Match foundation. |
| D-023 | accepted | Introduce a user-confirmed Evidence Profile as the factual source for generated application materials. | Shared provenance improves continuity and prevents fabricated employers, skills, metrics, credentials, and achievements. |
| D-024 | accepted | Evolve workspaces into Application Campaigns and pursue lawful, source-aware job discovery. | A role-specific campaign connects matching, materials, interview prep, tracking, tasks, and follow-up without becoming a generic CRM. |
| D-025 | accepted | Treat application automation as progressive trust levels: Copilot, Approval Queue, then source-specific Trusted Autopilot. | Automation is valuable, but ambiguous answers and unsupported sources require human approval and legal/terms controls. |
| D-026 | accepted | Prohibit unauthorized scraping, CAPTCHA/access-control circumvention, credential or session extraction, and unattended mass auto-apply. | These behaviors create platform, privacy, account, quality, and trust risks inconsistent with the product promise. |
| D-027 | accepted | Use `chapter2` as the long-lived experimentation branch while `main` and `deploy` remain stable promotion branches. | Product hardening and expansion need room to iterate without destabilizing the release and Railway deployment branches. |
| D-028 | accepted | Treat the eventual first release as a free private beta, while deferring launch operations and acquisition planning until engineering quality gates pass. | Engineering excellence is the immediate objective; billing and growth work would distract from measuring and improving the existing product. |
| D-029 | accepted | Use ephemeral distributed abuse counters with independent HMAC-pseudonymized account and source-IP dimensions; prefer bounded progressive login delay over account lockout, and add route-specific CAPTCHA only after the documented sustained-limit or provider-cost trigger. | Multi-instance enforcement must not store raw identifiers, let account rotation erase source limits, or create an attacker-controlled account-lockout denial of service. |
| D-030 | accepted | Preserve SameSite=Lax and reject logout requests whose explicit Origin is outside the configured frontend/CORS allowlist, while allowing non-browser clients with no Origin. | This prevents forced cross-site logout with a narrow compatibility-tested control instead of introducing a broader CSRF token protocol. |
| D-031 | accepted | Accept indefinite retention of primary account/content data while an account exists; deletion (single run or full account) is user-initiated and immediate with no grace period; no automatic dormant-account purge in V1. | User-initiated erasure already satisfies GDPR/RODO right-to-erasure; an automatic dormant-account purge needs a cron job and a user-notification flow disproportionate to thesis-demo/solo-dev scale. Resolves D-UNK-6 (primary data) and D-NEXT-3. |
| D-032 | accepted | Accept no database backups during the thesis-demo phase. Before public beta launch (R5), enable Railway's managed automated PostgreSQL backup add-on at its platform-default retention window, and rehearse a restore procedure as part of the R5 staging rehearsal in `docs/launch-checklist.md`. | Demo data is reproducible and non-critical, so backup infrastructure is deferred until real user data exists, consistent with D-021 (perfect the current product first) and R5's migration/rollback acceptance gate. Resolves D-UNK-7. |
| D-033 | accepted | Accept Railway's platform-managed log retention for application logs; no custom log persistence, export pipeline, or extended retention in V1. Logs must remain free of resume/JD/generated content and other sensitive fields per the existing scrubbing controls. | Structured, privacy-safe logs already avoid sensitive content (#78); a bespoke log-retention/export system is unwarranted operational overhead before user-scale evidence exists, consistent with the R10 deferred-scaling triggers. Resolves the logs portion of D-UNK-6. |
| D-034 | accepted | When Sentry is activated (`SENTRY_DSN` set), accept Sentry's platform-managed event retention as sufficient; no custom retention override or export is required. Sentry stays inactive by default. | Sentry SDKs already scrub PII/content (D-018); event retention duration is a processor-side setting that does not need product-level enforcement at this scale. Resolves the Sentry-events portion of D-UNK-6. |
| D-035 | accepted | Accept the single structured log line already emitted by `delete_all_user_data()` as the minimal deletion-audit record; no persisted audit-log table is required in V1. | Cascading account deletion is already transactional and logged; a dedicated audit table is speculative infrastructure without a demonstrated compliance requirement. Revisit only if legal/processor reconciliation (#82) demands durable audit evidence. Resolves the audit-records portion of D-UNK-6. |
| D-036 | accepted | For R6 Activation Instrumentation, extend the existing first-party telemetry pipe instead of reactivating PostHog or adopting a third-party analytics vendor. | See [ADR 0001](adr/0001-r6-instrumentation-backend-choice.md) for full alternatives/consequences; keeps the analytics vendor surface at zero and avoids reopening the unresolved PostHog processor question live in #82. |
| D-037 | accepted | Persist R6 activation/product-analytics events in a new, purpose-built `analytics_events` Postgres table, scoped strictly to the same low-cardinality allowlisted dimensions (event name, tool id, access mode, timestamps, duration, cost estimate) already permitted in frontend telemetry — never raw log lines, stack traces, or free-text content. Retain rows for a rolling 180 days with a scheduled prune job. | Distinct in scope from D-033, which rejected a *general application-log* export/persistence pipeline, not a narrow product-metrics table; a fixed retention window is a deliberate minimization given the recent PostHog lesson about letting collected data linger unexamined. Revisit the window if the R6 baseline needs a longer lookback. |
| D-038 | accepted | Backend-computed operational metrics (per-tool `duration_ms` and an estimated LLM token/cost figure) are captured server-side in the same request path that already runs `log_tool_run_completed`/`log_tool_run_failed`, and written to `analytics_events` unconditionally, the same way those calls already log unconditionally today. | No client-side tracker or cookie is involved, so the existing cookie-consent gate (`getStoredConsent() === 'rejected'`) that governs frontend-reported telemetry does not apply; keeping this a separate backend-only write path avoids conflating client-observed behavior with server-observed cost/performance. |
| D-039 | accepted | Build the R6 funnel/failure view as a minimal read-only page inside the existing `/admin/*` panel rather than adopting a third-party BI tool or building a standalone dashboard app. | Consistent with D-016 (admin panel stays inside the main frontend); matches solo-dev/thesis-demo scale — plain aggregate tables/counts are sufficient until real usage volume argues otherwise. |
| D-040 | accepted | Close the R6 event-taxonomy gaps by wiring the two dead-on-arrival event names already reserved in the schema — `workflow_continued` (fire at the actual next-tool CTA) and `auth_signup_source` (fire at signup completion, capturing the originating surface) — and adding one new event, `landing_page_viewed`, to cover the taxonomy's currently-missing entry point. | `workflow_continued` and `auth_signup_source` exist today only as allowlist enum values in `frontend/src/lib/telemetry/client.ts` and `backend/app/schemas/telemetry.py` — neither is ever actually fired from a component. Landing has no view event at all. R6's acceptance gate ("landing → tool start → tool completion → connected next step → signup → revisit/export") cannot be satisfied without closing these three gaps. |
| D-041 | accepted | Build R8 evaluation sets from small, hand-authored synthetic resume/job-description fixtures only; never sample, anonymize, or derive eval fixtures from real user `ToolRun` content. | See [ADR 0002](adr/0002-r8-eval-fixture-data-source.md); extends the PostHog-incident lesson (D-036) to internal dev tooling, not just product analytics — de-identification of free-text resumes is unreliable and would create a second durable real-content store. |
| D-042 | accepted | Track Resume/Job Match score calibration via a per-fixture expected score band assigned at fixture-authoring time; an eval run flags any fixture whose actual blended score (`compute_blended_score` in `backend/app/services/quality_signals.py`) falls outside its expected band beyond a fixed threshold as a calibration miss, reported as a per-tool miss rate. | Gives a repeatable, reviewable calibration signal against a fixed synthetic corpus (D-041) without needing real user ground truth, which the project has already decided not to collect for this purpose. |
| D-043 | accepted | Track generative-tool (Cover Letter, Interview Q&A, Career Path, Portfolio Planner) groundedness with a deterministic heuristic that traces every proper-noun/employer/quantified claim in generated output back to the source resume text, flagging untraceable claims as fabrication candidates; track usefulness with an LLM-as-judge score from the same Gemini Flash provider, against the fixture's job description. | A deterministic first-pass fabrication check is cheap, auditable, and reuses existing keyword-matching primitives (`quality_signals.keyword_present`); usefulness needs judgment a keyword check can't supply. Same-provider judge bias is an accepted, documented V1 limitation, not a blocker — a second-provider judge would reopen the single-provider scope decision (D-006). |
| D-044 | accepted | Run tool regression evaluation on demand via a CLI script, required before any prompt/model change ships (i.e. before bumping a tool's `_PROMPT_VERSION` constant in `backend/app/prompts/`), not wired into CI. | Live Gemini calls are slow, costly, and rate-limited; forcing them into every CI run would make the pipeline flaky and expensive, consistent with R2's precedent of keeping live-provider calls outside the deterministic CI boundary. |
| D-045 | accepted | Report eval-run results (calibration miss rate, fabrication-candidate count, usefulness score) as versioned JSON artifacts on disk, one per tool per run, surfaced read-only in the existing R6 admin dashboard (#108) alongside per-tool latency/cost — not persisted into the `analytics_events` table (D-037) and not a new BI tool. | Eval results are internal dev-tooling output, not user behavior data; keeping them out of the user-analytics table avoids scope creep of D-037, and reusing the existing admin panel matches D-016/D-039. |
| D-046 | accepted | Keep R9 provisional and candidate-neutral until the R6 implementation has produced its two-week baseline and D-NEXT-6 has an accepted activation target; no ad, subscription, or hybrid candidate may ship live from the pre-evidence backlog. | Actual completion, continuation, revisit, export, cost, and failure evidence must choose the revenue hypothesis; selecting one now would silently reverse the roadmap's evidence gate. |

| D-048 | accepted | Make every monetized access decision server-authoritative and withhold restricted payload fields at the server boundary; browser state may render a decision but never create or prove an entitlement. | See [ADR 0003](adr/0003-r9-server-authoritative-access-decisions.md); the historical `sessionStorage` ad unlock is user-tamperable and the current API already sends the complete result before the client wrapper renders. |
| D-049 | accepted | Dark-ship the selected R9 treatment behind a default-off server-controlled kill switch, retain the unchanged full-access experience as the control and accessible fallback, assign only eligible users without sensitive career attributes, and predeclare stop conditions for activation, retention, failures, cost, accessibility, and trust complaints. | A bounded experiment must be immediately reversible, measurable against a real control, and incapable of trapping a user behind an inaccessible or deceptive path. |
| D-050 | accepted | Measure R9 through the R6 first-party allowlisted analytics path, adding only low-cardinality candidate/cohort/outcome fields; do not reactivate PostHog or adopt a separate product-analytics vendor for monetization. | D-036 already chose the privacy-vetted first-party path, while the historical PostHog incident and cloud-project follow-up remain unresolved and explicitly outside R9 authorization. |
| D-051 | accepted | Remove the dormant `AdGatedLock`/`useAd`/`useAdUnlock` client monetization path and stale ad telemetry/storage contract before building an R9 candidate; do not revive it by deleting the thesis-demo early return. | Hooks run before the early return today, and `useAd` treats pending consent as sufficient, so a locally configured `VITE_AD_CLIENT_ID` can load an advertising script even while the UI appears fully bypassed. | D-052 | accepted | Keep R10 provisional and trigger-driven: first establish an aggregate operational scorecard, then authorize only the response whose predeclared scaling trigger has sustained evidence; do not bundle Redis, provider fallback, streaming, CAPTCHA, database pruning, or source adapters into a speculative platform rewrite. | The current Railway process is single-worker, R6/R8 implementation is still open, and no production traffic/capacity evidence shows which candidate response is needed. | D-053 | accepted | Extend the R6 first-party operational path for R10 trigger evidence and admin reporting, using allowlisted aggregates for replica/topology, cache outcome, provider incident category, phase latency, rate-limit/cost pressure, database health, and job-source family; never raw resume/JD/generated content, full URLs, provider exceptions, or stable user/run/workspace identifiers. | R10 needs evidence that can select a response without creating another analytics vendor or reconstructing sensitive user activity; the existing first-party table/dashboard boundary is already accepted by D-036–D-040. |
| D-054 | accepted | Keep result caching an optional, fail-open acceleration layer rather than a correctness, persistence, authorization, or coordination source; review a distributed backend only after multi-instance topology and duplicate-cost/cache evidence justify it, and keep cached result payloads inside the same sensitive-data boundary as `ToolRun.result_payload`. | See [ADR 0004](adr/0004-r10-cache-remains-fail-open-acceleration.md); the current in-process cache can miss across replicas without corrupting state, while making Redis authoritative would create a new availability and data-lifecycle dependency. |
| D-055 | accepted | Evaluate provider fallback only after the provider-incident trigger fires and the alternative passes the R8 synthetic quality suite, privacy/processor review, cost/latency comparison, and tool-specific failure semantics; use a server circuit breaker and do not hedge requests by default. | An unevaluated provider can silently reduce groundedness or fabricate content, while hedging doubles sensitive-content processing and model cost. | D-056 | accepted | Prefer real server phase progress over token streaming as the first latency response: expose bounded sanitize/cache/provider/persist/finalize state while persisting and returning only the final validated JSON result; do not create partial `ToolRun` rows or treat the existing cinematic timer as server progress. | All six tools depend on structured JSON and frontend Zod validation, so partial tokens are not yet a safe product contract. | D-057 | accepted | Escalate abuse/cost controls through the existing D-029 evidence path: tune bounded account/source quotas first, then add a reviewed challenge contract only to the attacked flow; never enable one global CAPTCHA switch as an automatic incident response. | Route-specific pressure needs a route-specific response, while a global challenge can block unaffected users and the current CAPTCHA contract covers registration only. |
| D-058 | accepted | Scale PostgreSQL from measured query plans and capacity evidence: add only additive composite indexes or bounded query changes that address observed hot paths, capacity-plan before saturation, and do not auto-delete primary account, workspace, or `ToolRun` data to control growth without explicitly superseding D-031. | Indefinite primary-data retention while the account exists is an accepted product contract; speculative indexes add write/storage cost, and silent retention changes would violate user expectations. |
| D-059 | accepted | Measure job-import reliability by an allowlisted source family (for example, supported ATS family versus `other`), never by full URL; build a domain/source adapter only after concentrated failure evidence and terms review, with a source-specific kill switch and paste fallback, otherwise reduce the supported scope honestly. | Raw URLs can contain identifying paths/query data, and generic scraping complexity should not grow for one unsupported source. A bounded source family is sufficient to decide whether specialization is justified. |
| D-060 | accepted | Keep R11 provisional and implementation-deferred until the R1–R4 gate closes (R3 remains in specification re-grill): this cycle defines the Evidence Profile contract that R12 CV Studio and R13 Campaigns depend on, and authorizes no schema, endpoint, or UI to ship before the gate. | Building a durable store of sensitive career claims on an unverified privacy/security posture would invert D-021, while leaving the contract undefined would let R12/R13 pre-commitments drift toward incompatible profile shapes. |
| D-061 | accepted | Model the Evidence Profile as a persisted, per-user, server-side collection of typed evidence items (experience, achievement, skill, education, project, certification, preference, reusable interview evidence), each carrying provenance (`imported`, `inferred`, `user-entered`) and confirmation state (`unconfirmed`, `confirmed`, `rejected`); do not derive it from session storage, workflow carry, or the latest `ToolRun`. | See [ADR 0005](adr/0005-r11-evidence-profile-persistence-boundary.md); resume text today is ephemeral tab-scoped state re-supplied inline on every request, and per-run "evidence" fields are unverified model-derived output, so no existing structure can carry a durable user-confirmed factual record. |
| D-062 | accepted | Only an explicit user action can move an evidence item to `confirmed`; resume parsing, tool-run outputs, and model inference may create or update items only as `unconfirmed` with recorded provenance, and a rejected item is excluded from all downstream use. | The profile's value is that confirmation means a human vouched for the claim; any automated confirmation path would let generation launder its own inferences into "verified" facts. |
| D-063 | accepted | Inject profile evidence into tool execution only through the shared pipeline seam, extending the existing locked-payload/prepass split: confirmed evidence enters prompts as locked facts that generation may reframe but never alter or extend; unconfirmed evidence is excluded from generation or surfaced only as an explicit gap or suggestion; the profile version participates in the result cache key. | `run_tool_pipeline()` is the accepted single execution seam (D-004) and the locked-payload prompt rule is the existing anti-fabrication mechanism; per-tool profile wiring would create six divergent trust paths, and a cache unaware of profile changes would serve stale evidence. |
| D-064 | accepted | Keep the Evidence Profile authenticated-only: guest flows continue to use tab-scoped carry and inline inputs, and no anonymous profile rows exist server-side. | Consistent with D-009 (guest runs are never persisted) and D-011; a durable server-side store of guest career claims would contradict the accepted guest data posture. |
| D-065 | accepted | Bring the Evidence Profile into the D-031 lifecycle contract: user-initiated correction, rejection, and deletion of single items or the whole profile are immediate; account deletion cascades over profile data in the same transactional path as existing user data; and R11 adds a self-serve machine-readable profile export. | The roadmap acceptance gate requires accepted retention, export, and deletion behavior; today only per-run PDF export exists, which cannot satisfy portability for a canonical evidence store. |
| D-066 | accepted | Keep historical `ToolRun` rows immutable snapshots: profile edits never rewrite past results, past runs never silently backfill the profile, and importing evidence from a parsed resume or a prior run is always an explicit, user-visible action. | Append-only run history (D-010) is an accepted auditability contract, and silent backfill would mass-create unconfirmed claims the user never saw, defeating the confirmation model. |
| D-067 | accepted | Treat all evidence item content as sensitive career content inside the existing observability boundary: analytics and telemetry may record only allowlisted low-cardinality profile events (item kind, provenance class, confirmation-state transition, bounded counts) — never evidence text, employer or institution names, or stable content identifiers. | The first-party allowlist boundary (D-036–D-038, D-053) already answers operational questions without reconstructing sensitive content, and the PostHog incident showed what lingering rich behavioral data costs. |
| D-068 | accepted | Keep R12 provisional and implementation-deferred until R11 ships behind the closed R1–R4 gate: this cycle fixes the CV Studio contract (document model, trust rules, export obligations) so R11 entities are built variant-ready, and authorizes no schema, endpoint, editor, or export to ship earlier. | CV Studio is the flagship expansion and every layer it needs — structured parsing, DOCX generation, templates, print QA — is greenfield; committing its contract now prevents R11 from persisting an evidence shape the studio would immediately have to migrate. |
| D-069 | accepted | Model the CV as its own persisted, per-user structured document entity — typed sections and entries whose factual claims reference Evidence Profile items — with one editable working draft per document plus immutable, recoverable variant snapshots; do not store CV documents as `ToolRun` payloads or as freeform rich text. | See [ADR 0006](adr/0006-r12-cv-document-model.md); `ToolRun` is an immutable single-shot snapshot chain with no editing semantics, freeform text cannot carry per-claim provenance or ATS validation, and layout/selection/ordering are durable user editorial choices the Evidence Profile alone cannot express. |
| D-070 | accepted | Import PDF, DOCX, and plain text through the existing isolated parser harness extended to produce structured extraction proposals that the user reviews and corrects before any CV document exists; imported factual claims flow into the Evidence Profile only through the R11 proposal path as `unconfirmed` items with `imported` provenance. | The subprocess isolation, resource caps, and upload guards are accepted hardened seams worth reusing; text-only extraction today cannot produce structured data, and a silent import would bypass the D-062 confirmation model. A `.txt` import path must be added since only PDF/DOCX are accepted today. |
| D-071 | accepted | Build CV Studio as a structured-section editor surface — add, hide, rename, reorder, and edit typed sections with accept/reject/edit controls — never a freeform document editor; it registers as a seventh registry entry without renumbering existing tools, but runs as an editor session surface rather than the single-shot submit→result tool pattern. | The roadmap gate explicitly excludes a freeform document-editor dependency; the current `ToolDefinition` contract models one submission producing one result and cannot express an editing session, while renumbering tool priorities is a standing repository constraint. |
| D-072 | accepted | Score CV quality with the existing explainable deterministic-signal-plus-blend mechanism extended to the structured document, and implement ATS compatibility as deterministic structural checks (sections, text layer, fonts, links, page breaks, re-import machine-readability); never present a universal ATS score or ranking/interview/employment promise. | The prepass/locked-payload/blend pattern with heuristic fallback is the accepted scoring architecture (D-005, D-007), and the product-direction honest-claim rule forbids universal ATS promises; parse-safety checks are verifiable properties while a single "ATS score" is not. |
| D-073 | accepted | Generate tailored variants only from confirmed Evidence Profile items plus content already in the user's document; present every material change as a before/after diff carrying requirement and evidence provenance with accept, reject, or edit controls; a claim without confirmed supporting evidence can enter the document only through an explicit user confirmation step. | Extends D-062/D-063 into the editor: tailoring is the highest-pressure fabrication surface, and a diff the user must act on is the only reviewable form of "AI may reframe verified evidence but must not invent." |
| D-074 | accepted | Render preview, DOCX, and PDF deterministically from one structured document plus one of exactly three declarative initial templates (ATS Essential, Professional Editorial, Technical/Portfolio), and gate export changes behind automated visual, text-layer, link, page-break, and re-import validation — re-import verified with the product's own parser. | A single render source prevents preview/export drift; DOCX generation does not exist today and the current reportlab flowable path has no template, page-break, font, or link control, so both exporters are new and need validation gates from the start; three deep templates follow the accepted depth-over-quantity direction. |
| D-075 | accepted | Bound the studio's iterative cost and keep its content inside existing boundaries: model-backed tailoring/scoring calls run through the shared pipeline with bounded per-document regeneration quotas, parsing keeps its subprocess resource caps, and CV document content joins the sensitive-content boundary — deletion cascade, export surface, and allowlisted low-cardinality telemetry only. | An edit→tailor→re-score loop multiplies generation calls in a way single-shot per-route rate limits were never designed for, and a persisted CV is exactly the kind of sensitive career content D-031/D-067 already govern for the profile. |
